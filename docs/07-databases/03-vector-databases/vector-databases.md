# Vector Databases

## TL;DR

- **Vector databases** store and search high-dimensional vectors, often generated by machine learning models.
- They enable **semantic search**, where results are retrieved based on meaning rather than exact keyword matches.
- An embedding model converts text, images, or other data into numerical vectors.
- Similarity metrics such as cosine similarity and dot product help identify relevant vectors.
- Vector databases are commonly used for RAG, recommendation systems, and multimodal search.

## What Is a Vector Database?

A vector database stores vector embeddings along with associated metadata and, optionally, references to the original data.

An embedding is a numerical representation of an item in a vector space. Items with similar semantic content tend to have nearby representations, depending on the embedding model and its training objective.

For example, an embedding model might represent these sentences as vectors:

- "How can I reset my password?"
- "I forgot my login credentials."

Although the sentences share few exact words, their embeddings may be similar because they express related meanings.

Vector databases enable efficient similarity search across large collections of these vectors.

## How Vector Search Works

A typical vector search workflow consists of the following steps:

1. **Generate embeddings:** Use an embedding model to convert documents or other data into vectors.
2. **Store vectors:** Save the vectors and associated metadata in a vector database.
3. **Embed the query:** Convert the user's search query into a vector using a compatible embedding model.
4. **Find nearest neighbors:** Retrieve vectors that are closest to the query vector.
5. **Return results:** Provide the associated documents, metadata, or references.

The embedding model and database solve different problems: the model creates representations, while the database stores and retrieves them.

## Similarity Metrics

Vector databases use distance or similarity measures to compare vectors.

**Cosine similarity**

Measures the cosine of the angle between two vectors:

$$
\text{cosine similarity}(A,B)
=
\frac{A \cdot B}{\|A\|\|B\|}
$$

It is often used for text embeddings when the angle between vectors is meaningful.

**Dot product**

Calculates the sum of the element-wise products of two vectors. Its magnitude can depend on vector lengths, so it is not always equivalent to cosine similarity.

**Euclidean distance (L2)**

Measures the straight-line distance between two vectors. Smaller distances indicate greater proximity.

The appropriate metric depends on the embedding model, its training objective, and the database configuration. Normalized vectors can make cosine similarity and dot-product rankings equivalent.

## Approximate Nearest Neighbor Search

Searching every stored vector can become expensive as datasets grow.

Vector databases often use **Approximate Nearest Neighbor (ANN)** algorithms to retrieve highly similar vectors without exhaustively comparing the query against every stored vector.

Common approaches include:

- **HNSW:** Builds a hierarchical graph for efficient nearest-neighbor search.
- **IVF:** Partitions vectors into clusters and searches selected clusters.
- **Product Quantization (PQ):** Compresses vector representations to reduce memory usage.

ANN search trades some retrieval accuracy for speed and resource efficiency. The trade-off depends on the algorithm and its parameters.

## Metadata Filtering

Vector search often combines semantic similarity with structured filters.

For example, a legal RAG system might restrict retrieval to a particular document type or client identifier.

Conceptually:

```python
results = vector_db.search(
    query_vector=query_embedding,
    top_k=5,
    filter={
        "document_type": "contract",
        "client_id": "client_123"
    }
)
```

This is illustrative pseudocode; actual APIs and filter syntax differ between databases.

Metadata filtering can improve relevance and help enforce retrieval boundaries. In multi-user applications, however, access restrictions must be enforced reliably by the backend. A user-supplied filter alone is not a security boundary.

## Vector Databases in RAG

Retrieval-Augmented Generation (RAG) combines document retrieval with a language model's generation capabilities.

A typical workflow is:

1. Split documents into chunks.
2. Generate an embedding for each chunk.
3. Store embeddings, chunk text or references, and metadata.
4. Embed a user's question.
5. Retrieve relevant chunks using vector search, optionally combined with keyword search and reranking.
6. Pass the retrieved context to the language model.
7. Generate an answer grounded in the available context.

The vector database supports retrieval but does not guarantee that the final answer is correct. RAG quality also depends on document parsing, chunking, embedding quality, retrieval settings, prompt design, and evaluation.

## Vector Databases vs. Traditional Databases

| Vector databases | Traditional relational databases |
|---|---|
| Optimized for vector similarity search | Optimized for structured queries and relational operations |
| Store embeddings and associated metadata | Store rows, columns, and relationships |
| Often use ANN indexes for large-scale retrieval | Use indexes such as B-trees for many common queries |
| Useful for semantic search and RAG | Useful for transactions, joins, and structured filtering |
| May offer limited or specialized relational capabilities | Typically provide rich SQL and constraint support |

The distinction is not absolute. Some relational databases support vector extensions, allowing applications to combine structured queries and vector search in one system.

## Popular Vector Database Options

- **PostgreSQL with pgvector:** Adds vector storage and similarity search to PostgreSQL.
- **Qdrant:** An open-source vector search engine with metadata filtering.
- **Weaviate:** A vector database supporting vector and hybrid search.
- **Milvus:** A vector database designed for large-scale similarity search.
- **Pinecone:** A managed vector database service.

The right choice depends on deployment requirements, data governance, filtering needs, scale, latency, operational complexity, and cost.

## Evaluation and Best Practices

- Choose an embedding model appropriate for the domain and language.
- Use compatible embedding models for documents and queries.
- Tune chunk size and overlap based on the retrieval task.
- Select a similarity metric consistent with the embedding model.
- Evaluate retrieval with metrics such as Recall@k, Precision@k, and MRR.
- Compare approximate search quality against exact search on representative samples when feasible.
- Combine vector search with keyword search when exact terms, identifiers, or legal references matter.
- Apply authorization filters on the server side.
- Monitor latency, storage costs, and retrieval quality as the dataset evolves.
